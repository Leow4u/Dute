etapa 2; transporte da etapa 3 só passa dados já autenticados. Gestão usa token
Firebase humano; API usa token de integração. Revisar tentativa de usar um como
o outro, chave reutilizada por outro agente, aprovação de payload diferente,
revogação do delegante e documentos com campos extras sensíveis.

## Registro de execução

- Etapas 1–3 implementadas: gateway `duteApi`, gestão humana de credenciais,
  aprovações exatas, consultas e ações da Operação, OpenAPI e gate HTTP no deploy.
- Testes iniciais existentes: 214/214 unitários. Com a API: 219/219 unitários e
  134/134 de integração no emulador, incluindo o ciclo REST completo. Ferramentas:
  164/164 testes Python. Build de produção e typecheck da Operação verdes.
- Revisão independente: corrigidos os dois bloqueadores encontrados — campos
  anunciados que o domínio recusa e ausência dos IDs/saldo para planejamento.
  Acrescentada checagem transacional do cliente autorizado na OS, com regressão
  observada falhando e depois passando. Ciclo REST cobre saldo insuficiente sem
  efeitos parciais e edição desatualizada ao agendar.
- Decisão: manter idempotência por integração, tipo de ação e escopo de negócio,
  como no domínio existente; documentado que outra demanda é outro escopo.
- Respostas OpenAPI ganharam schemas explícitos e operationIds únicos.
- A API também carrega as Rules reais num teste do emulador e verifica que as
  três coleções novas recusam leitura/escrita até de um owner autenticado pelo
  SDK do cliente. Nenhuma regra de acesso foi ampliada.
- OpenAPI validado externamente com swagger-cli. O teste de contrato conserva
  operationIds únicos, headers obrigatórios de escrita e required não vazio.
- Publicação: a CLI GitHub não autentica (GH_TOKEN inválido). O conector permite
  PR/merge/leitura de CI, mas não oferece workflow_dispatch. Não substituir o
  fluxo oficial por deploy direto nem alterar credenciais para contornar isso.
  A etapa remota será registrada no PR e na resposta final conforme a evidência.
